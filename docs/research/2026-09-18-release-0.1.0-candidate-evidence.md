## Candidate-evidence durability gap

The main-push workflow already records `unsigned-candidate-receipt.json`, but the dedicated SignPath signing-input artifact intentionally contains only `wag-native-host.exe`. The verified three-file distribution also intentionally omits the unsigned candidate receipt.

That separation is correct for signing scope, but without a third artifact the strict receipt disappears with the ephemeral runner workspace. Release-readiness verification then cannot later pair the exact CI-built executable with its recorded unsigned provenance.

## Implemented shape

The branch preserves three distinct artifact roles:

1. `wag-native-host-signing-input-<sha>-attempt-<n>` - EXE only; future signer mutation surface.
2. `wag-native-host-candidate-evidence-<sha>-attempt-<n>` - `unsigned-candidate-receipt.json` only; immutable unsigned provenance evidence.
3. `wag-native-host-windows-x64-<sha>-attempt-<n>` - existing verified unsigned distribution (`wag-native-host.exe`, checksum, `build-receipt.json`).

The candidate-evidence artifact is main-push-only, uses the same pinned `actions/upload-artifact` revision, fails closed when missing, and retains evidence for 14 days. It does not widen SignPath signing input.

## Ordering invariant

`package.json` is a `NATIVE_HOST_BUILD_INPUTS` member. Therefore a version change invalidates candidate continuity and must occur before recording the final candidate receipt.

Required order:

`select version -> merge source -> CI build -> VersionInfo verification -> exact artifact tests -> record unsigned receipt -> persist evidence + signing input -> release-readiness verification`
